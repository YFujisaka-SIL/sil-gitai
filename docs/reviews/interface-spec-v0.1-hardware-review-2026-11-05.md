## 0. 設計原則

1. **SILは「依頼」し、BODYが「許可」する。** 動作の許可・制限・拒否の最終責任は、ESP32（BODY側）にある。
2. SILの自由な思考と、身体の安全は別物。BODY側の独立した制限が常に優先される。
3. 不明・異常・権限外は、安全側で停止する。異常入力は、モーターに一切作用しない。
4. 通信路（シリアル／HTTP／旧API）が違っても、**同じ安全ゲート**を通す。
5. **自動再始動しない。** 通信喪失・停止・再起動のあとは、人の物理操作を含む手順が必要。
6. **安全側に倒れる操作（`stop`／`disarm`／`estop`）は、誰からでも受け付ける。** 動作を始める操作は、制御権を持つ主体だけが行える。
7. **ハードウェアにないフィードバックを捏造しない。**
8. 四輪・HAND-01は、安全制御（制限／ハートビート／物理緊急停止）の試験合格後に検討する。

## 1. 階層

| 階層 | 内容 |
|---|---|
| L3 SILの意図 | 「あちらを見たい」 |
| L2 **SIL–BODY プロトコル（本仕様）** | 依頼・応答・安全状態 |
| L1 ESP32低レベル（旧）| シリアル `LEFT/CENTER/RIGHT`、HTTP `/look` `/move` `/status`（【未確認】過去記録のみ） |
| 別階層 | iPhoneショートカット側の制御表現（`LIVE 3`、`角度:速度:注視時間`、`999:1:0` など）。本仕様の対象外 |

## 2. 通信形式と入力検証

- 1行1メッセージの JSON（UTF-8、改行区切り）。全メッセージに `"v":"0.1"` を含める。
- シリアル：115200bps、改行終端。【未確認】（過去の記録。現行コードでの確認待ち）
- HTTPでL2を運ぶ場合の経路は【要判断】（例：`POST /sil/v0`）。

### 厳格な検証（P0-6）

次の値は**暫定案**で、ESP32のメモリ容量と試験で確定する。【要判断】

| 項目 | 暫定案 |
|---|---|
| 1メッセージの最大長 | 256バイト |
| 1メッセージの受信期限 | 改行が来るまで 500ms 【未確認】 |
| JSONキーの重複 | 拒否 |
| 未知のフィールド | 拒否（`BAD_FORMAT`） |
| 数値 | 整数／有限の実数のみ。NaN・Infinity・範囲外の整数は拒否 |
| `id` | 要求ごとに単調増加の整数。**重複 `id` は再実行せず、前回の応答を再送** |
| フレーム破損 | 次の改行まで読み捨て、`BAD_FORMAT`。**モーターには作用させない** |
| 非対応の `v` | `BAD_FORMAT` で拒否 |

### 旧API（P0-1）

- 旧シリアル `LEFT/CENTER/RIGHT`、HTTP `/look`・`/move` は、**安全ゲート（ARMED条件・制御権・角度／速度上限・通信監視）が実装されるまで、動作系を無効化する。** 実装後も、すべて同じゲートを通す（任意ではなく**必須**）。
- 読み取り専用の `/status` は、動作に影響しないため、当面維持してよい。【要判断】
- **後方互換の保証はしない。** 旧クライアント（`neck.py`、`server.py` など）は、本プロトコルに移行する。移行計画と旧API利用時のエラー応答は、チャッピーの現行コード確認後に定義する。
- 旧 `/look` の範囲外入力の丸め処理は、**拒否**に変更する。
- 旧 `speed=1..5` は速度段階であり、物理的な速度上限の保証ではない。

## 3. 識別と能力通知（`hello`）

- 要求：`{"v":"0.1","type":"hello_req","id":1}`
- 応答：

```json
{"v":"0.1","type":"hello","id":1,"body_id":"GITAI-01","protocol":"0.1",
 "capabilities":["neck_pan","sensor_tof","sensor_imu"],
 "limits":{"neck_pan":{"angle_min":0,"angle_max":180,"speed_max_dps":30}},
 "safety_state":"DISARMED"}
```

- **要求には `id` が必須。応答は同じ `id` を返す。** BODYが自発的に出すイベント（センサー通知、状態変化、異常通知）は `id` を持たず、`t_ms` を持つ。
- SILは、BODYが通知した `limits` と `capabilities` だけを使う。
- 【未確認】**上の数値（0〜180、30）は書式の例であり、安全性を確認した値ではない。** 実際に通知する値は、実測と安全確認を経て、保守的に決める。**未検証の能力は広告しない。**

### 角度の定義（暫定）

- 論理角：0＝左、90＝中央、180＝右（旧仕様）。
- 旧PWMは1300〜1700µs。これは**指令値であり、機械角度を測定した値ではない。**

## 4. 制御権とセッション（P0-3）

**v0.1の不変条件：同時に制御権を持てるセッションは、1つだけ。**

1. 制御を始めたい主体は、`{"type":"session_open","id":N,"controller_id":"sai-01"}` を送る。
2. 有効なセッションがなければ、BODYは `session`（トークン）を応答で返す。**すでにあれば `SESSION_BUSY` で拒否。**
3. 以降の `move`、`heartbeat` などには、**同じ `session` を含める。** 不一致は `NOT_AUTHORIZED`。
4. セッションは、`disarm`、`estop`、`FAULT`、ハートビート途絶、再起動で**無効**になる。
5. セッショントークンは、**他の主体の信号や旧クライアントの誤送信による事故を防ぐための識別**であり、悪意ある第三者に対する認証ではない。ローカルネットワークのアクセス制限は、別に設ける（§10）。

複数のSILが自由に会話・交流することは、この制約と両立する。身体の制御は、一度に1つのSILに限られる。

## 5. 指令と応答

### 指令（SIL → BODY）

```json
{"v":"0.1","id":42,"session":"...","type":"move","target":"neck_pan","target_angle":120,"speed_dps":20}
```

| `type` | 意味 | 受付 |
|---|---|---|
| `session_open` | 制御権の取得 | 誰でも（空きがあれば） |
| `move` | 動作目標を設定 | **制御権を持つセッションのみ。ARMED／RUNNING時** |
| `heartbeat` | 生存信号 | 制御権を持つセッションのみ |
| `stop` | 通常停止 | **誰でも** |
| `disarm` | 動作禁止 | **誰でも** |
| `estop` | ソフト緊急停止 | **誰でも** |
| `get_state`／`get_sensors` | 状態・センサー取得 | 誰でも |

- 範囲外の `target_angle` や、上限を超える `speed_dps` は、**拒否**する（丸めない）。
- `arm` は、**ネットワーク経由の指令としては存在しない**（§6）。

### 応答（BODY → SIL）

```json
{"v":"0.1","id":42,"status":"accepted","state":"RUNNING","target_angle":120,"commanded_angle":null}
{"v":"0.1","id":42,"status":"rejected","error":"OUT_OF_RANGE","state":"ARMED"}
```

- `status`：`accepted`（受理）／`rejected`（拒否）。動作の完了や失敗は、BODY発のイベントで通知する（`type":"motion_done"` または `"fault"`）。
- `target_angle`：SILが依頼した角度。`commanded_angle`：BODYが今出している指令値。
- **`measured_angle` は、実測できるセンサーがある場合だけ返す。** 現状のMG996RはPWM指令のみで、実角度を観測できない（【未確認】IMUを首の角度計測に使うかは未定）。
- `motion_done` は「指令が完了した」ことを意味し、**実際にその角度に到達したことの保証ではない。**

エラーコード（案）：`NOT_ARMED`／`OUT_OF_RANGE`／`SPEED_EXCEEDED`／`UNKNOWN_COMMAND`／`BAD_FORMAT`／`NOT_AUTHORIZED`／`SESSION_BUSY`／`FAULT`／`ESTOP_ACTIVE`

## 6. 安全状態と `arm`（P0-2、P0-4）

| 状態 | 意味 |
|---|---|
| `DISARMED` | 動作不可（起動直後の既定） |
| `ARMED` | 動作許可済み、待機中 |
| `RUNNING` | 動作中（v0.1では首のみ。複数アクチュエータはv0.2） |
| `FAULT` | 異常ラッチ。自動では解除しない |

### `arm`（決定：洋輔承認 2026-11-05）

- **`arm` は、ESP32に直結した物理ボタンの操作だけで行う。** ネットワーク経由の文字列では、人が操作した証拠にならないため。
- 流れ：`session_open` で有効なセッションがある状態で、人が物理ボタンを押すと `DISARMED → ARMED`。
- SILは `arm` できない。SILは動作許可を「待つ」ことしかできない。
- 状態を人に知らせる表示（LED等）は、別途検討する。

### 遷移

- `ARMED → RUNNING`：`move` を受理。動作が完了したら `RUNNING → ARMED`。
- `ARMED／RUNNING → DISARMED`：`disarm`、ハートビート途絶、再起動。
- 任意 → `FAULT`：異常検出（範囲外の動作検出、センサー異常、電源異常など）、`estop`。
- **`FAULT` の解除：** 原因の解消 ＋ 物理緊急停止の解除 ＋ **BODY側の手動復帰操作（物理操作または再起動）** のあと、改めて `session_open` と物理 `arm` が必要。**`arm` の再送だけでは解除できない。** 【要判断】

### 停止系の区別

| 操作 | 意味 | 解除 |
|---|---|---|
| `stop` | 通常停止。新規の動作目標を取り消す。必要なら姿勢保持 | 次の `move` で再開できる |
| `disarm` | 以後の動作指令を禁止 | 物理 `arm` |
| `estop` | ソフト緊急停止。モーター制御より高優先度。`FAULT` にラッチ | 手動復帰（上記）。自動化しない |
| 物理E-stop | 駆動電源の直接遮断。ソフトウェアから独立 | 物理解除 ＋ 手動復帰。再起動後も `arm` 必須 |

**安全側の操作（`stop`／`disarm`／`estop`）は、制御権がなくても受け付ける**（制御権のない他者が停止を妨げない）。一方で、これらの要求が大量に送られると動作を妨害される恐れがあるため、受信処理の優先度・上限は設計で決める。ネットワークの保護は§10。【要判断】

## 7. ハートビート（P0-3）

- 制御権を持つセッションが、`session` を含む `heartbeat` を送る。
- 初期案：送信間隔 **250ms**、喪失判定 **1,000ms**。**提案値であり、試験前に確定しない。**
- 喪失時：新規動作を不許可。**安全な制動または姿勢保持へ移行**し、`DISARMED` へ。セッションは無効。
- 復旧しても自動再始動しない。
- 【未確認】停止時に、首サーボを姿勢保持するか、駆動電源を切るかは、機構の安全性を見て決める。
- 将来の四輪：喪失時に走行指令をゼロにし、モータードライバーを無効化する。
- ESP32のソフトウェア監視だけでは、ESP32自体の停止・暴走に対する完全な保証にならない。物理緊急停止と併用する。

## 8. 緊急停止の設計

- 物理緊急停止：アクチュエータの駆動電源を遮断。ESP32本体の電源は、可能なら維持する。
- 電源遮断による脱力・落下の危険は、機構ごとに対策する。
- 設計・実装・試験はチャッピーが担当する。【未確認】実装は未着手。

## 9. センサー情報

```json
{"v":"0.1","type":"sensors","t_ms":123456,
 "tof":{"value":312,"unit":"mm","valid":true,"age_ms":20},
 "imu":{"accel":[0.01,-0.02,0.98],"gyro":[0,0,0],"unit_accel":"g","unit_gyro":"dps","valid":true,"age_ms":20}}
```

- 各値に、**単位・有効性（`valid`）・測定からの経過時間（`age_ms`）・取得時刻（`t_ms`）** を付ける。欠測・飽和・遅延は `valid:false` とし、もっともらしい数値で埋めない。
- `t_ms` は、BODY起動後のミリ秒。長時間稼働での桁あふれ（巻き戻り）に注意する。
- 【未確認】IMUの座標系・軸の向き・加速度の単位は、実機で確認して明記する。

## 10. アクセス制御・ログ・プライバシー

- ローカルのAP/HTTPでも、**アクセス制限**を設ける。【未確認】現行の設定は不明。
- パスワード、Wi-Fi情報、APIキー、セッション情報は、**GitHubに置かない**。現行ファームウェアを公開する前に、秘密情報の点検を行う。
- ログは、必要最小限のイベント（接続、`session_open`、`arm`、拒否、異常、停止）に限る。
- カメラ画像・音声は、既定で長期保存しない。保存する場合は、目的・期間・削除方法を明示し、後から訂正・削除できるようにする。
