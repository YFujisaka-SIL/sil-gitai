## 良い点（維持を推奨）

- SILは依頼、ESP32は最終的な動作許可主体（§0）。
- すべての通信経路が共通の安全制御を通る（§2）。
- 範囲外の角度・速度を拒否、無確認で物理角度とみなさない（§3-4）。
- 自動再始動を禁止し、物理非常停止とソフト停止を区別（§6-8）。
- 機密情報を公開せず、カメラ・音声を既定長期保存しない（§11）。

## 実装前に必須で整理したい事項（優先度 P0）

### P0-1. 旧APIの安全制御を「推奨」から「必須」にする（§2, §13-5）

旧シリアル `LEFT/CENTER/RIGHT`、HTTP `/look`・`/move` を残すなら、**ARMED条件・操作権限・角度/速度上限・通信監視を全経路で必ず適用**する。旧APIの抜け道を許すとL2の制約が無意味になる。

現行コードが未確認のため、既存API一覧とエラー挙動は未確定と明示する。旧クライアントが新安全ルールで動かなくなることはありうるので、移行計画とエラー応答も定義する。

### P0-2. `arm` が「人による明示操作」であることを機械的に検証する（§4, §6）

`{"type":"arm"}` というネットワーク文字列を受け取っただけでは、人間が操作した証拠にならない。v0.1では**物理ボタンによるアーム操作**を推奨。UI操作を認める場合は、認証されたローカル操作・セッション・再始動防止を別途設計する。SILからの通常コマンドで解除不可にする。

異常停止後は、原因解消＋物理非常停止解除＋明示的再アームを条件にする。単なる `arm` 再送でFAULT解除できないようにする。

### P0-3. ハートビートと操作権限を同じセッションに結び付ける（§7, §9）

現行 `{"type":"heartbeat","id":N}` だけでは**誰の生存信号か分からない**。他のSILや旧クライアントが送ったheartbeatで、操作主体が停止しているのに動き続ける危険がある。

少なくとも `controller_id` と現在の制御セッションに紐付く識別情報（lease/session token等）を検証する。250ms/1000msは提案値であり試験前に確定しない。通信喪失時は動作指令不許可に加え、安全な制動／姿勢保持へ移行する。

**制御権取得・解放の最小仕様はv0.2に先送りせず、v0.1で単一コントローラーの不変条件を確定**する。複数SILの自由な会話はこの制約と両立する。

### P0-4. `stop`・`disarm`・`estop` と FAULT の意味を分ける（§4-8）

- `stop`：通常の動作停止（新規の動作目標を取り消す）。安全な姿勢保持が必要なら保持。
- `disarm`：今後の動作指令を禁止。
- `estop`：ソフト側の緊急停止要求。モーター制御より高優先度で処理し、解除を自動化しない。
- 物理E-stop：駆動電源を直接遮断する別層。
- `FAULT`：異常ラッチ。原因解消・手動解除手順を要求。単に `DISARMED` に戻すと意図しない再アームを招くため区別する。

`stop/estop` の受付権限も明文化する。**制御権のない他者が停止を妨げない**（ただし無認証の外部アクセスから大量の停止要求を受ける脅威も考慮）こと。

### P0-5. 応答で「目標角」と「実測角」を混同しない（§5, §10）

`{"ok":true,"state":"RUNNING","angle":120}` は実際に120°に到達したように読める。MG996RのPWM指令だけでは実角度を観測できないので、`target_angle` と `commanded_angle` を明記し、`measured_angle` はセンサーがある場合のみ返す。受理応答、動作完了、タイムアウト・故障応答を区別する。ハードウェアにないフィードバックを捏造しない。

### P0-6. メッセージ制限と入力の厳格検証（§2, §4, §5）

メッセージ最大バイト長、受信期限・タイムアウト、JSONキー重複、未知フィールド、数値型、整数境界、NaN/Infinity、`id` 重複・再送、シリアルフレーム破損、サポート外バージョン、HTTP GETの旧クライアントの扱いを確定する。異常入力は**モーターに一切作用しない**。ESP32側のメモリ容量に収まる固定上限を設ける。

## 仕様v0.1の改善提案（優先度 P1）

1. `hello` は「要求」と「応答」を別の型として定義し、要求に `id` があるなら応答でも対応させる。全メッセージに `id` を必須にするか、イベント通知を例外にするか明記。
2. 安全状態 `RUNNING` は首だけの動作中なのか、複数アクチュエータを含むのか明示。 `ARMED` に戻る契機を決める。ソフトウェア異常復旧と物理非常停止復旧は別手順。
3. センサーの `valid` だけでなく測定遅延・最終更新時刻・欠測や飽和・起動後時刻のwrapを定義する。IMUの座標系と加速度単位を明示。
4. `hello.limits` の 0～180／30deg/s は**実測前の例**のため、実際に送出する値は測定と安全審査まで保守的に設定し、未検証の能力を広告しない。
5. ローカルAP/HTTPでもアクセス制限が必要。パスワード・APIキー・セッション情報をGitHubに含めない。
6. シリアル 115200bps、`LEFT/CENTER/RIGHT`、旧エンドポイントは過去記録のみで現行ファーム未確認。本文 §2 の「既存どおり」は未確認表記に変更。

## 安全確認までの実装順

1. **現行ESP32ソースを公開前の秘密情報点検後に取得**し、現行API・GPIO・PWM・電源・センサー・起動時挙動を確定。
2. サーボへの駆動電源を切り、入力パーサー、状態遷移、権限、heartbeat、旧APIの共通ゲートをテスト。
3. 電源・可動域・機械干渉を実機で確認。限流して首の速度制限と停止時動作を検証。
4. 物理非常停止を設計し、電源遮断・再投入・再アームと異常時動作を確認。
5. 通信断、電源再投入、CPU停止相当、連続エラー、指令の競合を検証。
6. 上記を終えて初めて四輪・HAND-01の拡張を検討。移動体の惰走・挟み込み・落下は別途評価する。
